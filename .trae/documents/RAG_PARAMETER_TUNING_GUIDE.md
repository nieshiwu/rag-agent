# RAG 系统参数调优指南

本文档旨在为 RAG (Retrieval-Augmented Generation) 系统中的关键参数选择提供工程化指导，重点关注 `top_k` 的评估与选择。

## 1. Top-K (检索数量) 选择指南

`top_k` 定义了从知识库中检索并提交给 LLM 的文本片段数量。

### 1.1 核心权衡矩阵

| 维度 | Top-K 较小 (1-3) | Top-K 较大 (5-10+) |
| :--- | :--- | :--- |
| **召回率 (Recall)** | 低 (容易漏掉关键信息) | 高 (覆盖面广) |
| **精确率 (Precision)** | 高 (通常只有最相关的) | 低 (包含大量噪声) |
| **Token 成本** | 低 | 高 |
| **LLM 响应速度** | 快 | 慢 |
| **幻觉风险** | 较低 (但可能回答"不知道") | 较高 (可能基于错误片段胡编) |
| **迷失中间风险** | 无 | 高 (LLM 忽略中间内容) |

### 1.2 推荐配置策略

根据系统架构的不同，推荐以下两种配置模式：

#### 模式 A：直接检索 (Direct Retrieval)
*   **架构**: Query -> Vector Search -> LLM
*   **现状**: 本项目 (`rag_agent`) 当前采用的模式。
*   **推荐值**: **3 - 5**
*   **理由**: 向量检索在 Top 5 之后的相关性通常大幅下降。引入低相关性片段会显著增加噪声，导致 LLM 性能下降。

#### 模式 B：重排序 (Reranking)
*   **架构**: Query -> Vector Search (Broad) -> Reranker Model -> LLM
*   **推荐值**:
    *   **检索阶段 (Retrieval top_k)**: **20 - 50** (确保高召回)
    *   **重排阶段 (Rerank top_n)**: **3 - 5** (确保高精度)
*   **理由**: 先用大网捞鱼，再用精细模型筛选，是目前 RAG 的最佳实践。

### 1.3 基于任务类型的微调

| 任务类型 | 示例问题 | 推荐 Top-K | 说明 |
| :--- | :--- | :--- | :--- |
| **事实查证** | "张三的工号是多少？" | **1 - 2** | 答案唯一，不仅需要准确，还需要排除干扰。 |
| **综合问答** | "如何评价该公司的财务状况？" | **5 - 10** | 需要综合收入、支出、利润等多维度信息。 |
| **代码辅助** | "如何使用这个 API？" | **3 - 5** | 需要函数定义、参数说明和示例代码。 |

## 2. Chunk Size (切片大小) 配合

`top_k` 的选择必须与 Chunk Size 联动，需确保总 Token 数在 LLM 的舒适区内。

*   **公式**: `Total_Input = Prompt + Query + (Chunk_Size * top_k)`
*   **示例**:
    *   如果 Chunk Size = 500 tokens, top_k = 5 -> Context = 2500 tokens (安全)
    *   如果 Chunk Size = 2000 tokens, top_k = 5 -> Context = 10000 tokens (昂贵且慢)

## 3. 调试与监控建议

1.  **监控 "无结果" 率**: 如果 Agent 频繁回复“未找到相关信息”，考虑适当增加 `top_k`。
2.  **监控 "幻觉" 率**: 如果 Agent 经常基于错误的片段回答，考虑减小 `top_k` 或引入 Rerank。
3.  **使用 `confidence_score` 截断**: 不要只依赖固定的 `top_k`，建议结合 `score_threshold`（如只保留置信度 > 0.7 的结果）。
